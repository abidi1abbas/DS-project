Phase 1 is done, and Phase 2 is now the final phase of the project. The last date is 28th November, and your complete project should be ready by then. There will be no extensions, so plan your time accordingly.

In this phase you build on the work from Phase 1. What you need to deliver depends on the type of project you are doing.

If your project is a traditional ML/DL project (training your own models):

- Model building: apply suitable models to your problem (more than one if possible, so you can compare them)
- Training and testing: a proper train/test split, with cross-validation or hyperparameter tuning where it makes sense
- Evaluation: the right metrics for your problem (accuracy, precision, recall, F1, RMSE, R2, etc.), with confusion matrices, plots or comparison tables
- Comparison and analysis: which model performed best and why, where it fails, and what could be improved
If your project uses pre-trained LLMs (LangChain, RAG, agents, etc.):

You won’t have a model training phase, but you still need to show that your system actually works well. Instead of training, I expect:

- Pipeline design: a clear explanation of your architecture (which LLM, embeddings, vector store, chunking strategy, prompts, chains or agents, and why you chose them)
- Experiments: try at least a few different configurations (different LLMs, chunk sizes, retrieval settings, prompt versions, etc.) and compare them
- Evaluation: test your system on a set of sample questions or tasks and judge the quality of the outputs. Use whatever fits your project: accuracy on a test set, retrieval quality, response relevance, hallucination checks, response time, or manual scoring with a small table. Show your results, don’t just say it works.
- Limitations and analysis: where does your system fail or give wrong answers, and what could be improved
- Prompts and configs: keep your prompts, config files and any fine-tuning or embedding scripts in the repo
- API keys: never push API keys to GitHub. Use a .env file, add it to .gitignore, and include a .env.example showing which variables are needed
For everyone:

- Working website: your project must have a working website or web app where a user can give input and get results from your system (Streamlit, Flask, FastAPI, Gradio or any framework you prefer)
- Deployment: it will be appreciated if your website is deployed online (Streamlit Community Cloud, Hugging Face Spaces, Render, Railway, etc.). Add the live link in your README. If you can’t deploy it, make sure it runs properly locally and the README has clear steps to run it.
- Conclusion: a final summary of what your project achieved and what the results mean in practice
What your GitHub repo should contain at the end:

- An updated README.md covering the problem statement, dataset details, a summary of your Phase 1 work, the models or pipeline used, final results, the live website link (if deployed), and instructions to run the project
- Notebooks (.ipynb) for the modeling or experimentation work, with markdown cells explaining your steps and all outputs visible
- Website code (app files, templates, etc.) in its own folder
- Graphs and result visuals, such as model or configuration comparison charts, evaluation plots and feature importance
- The trained model files if they are not too large (or a script that reproduces them), or for LLM projects, your pipeline code and any vector store or index creation scripts
- requirements.txt with all the libraries you used
- A clean, organized repo structure, with Phase 1, Phase 2 and the website clearly separated
